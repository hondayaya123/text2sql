Q1. CHESS 論文的 "Full Information" 策略

CHESS 把 context 分三個等級做對照實驗：

❌ Reduced Info（基本款，大多數系統）

只給 table name + column name

→ SELECT * FROM CP_WAFER WHERE ...

⚠️ Basic Info（一般款）

加上 column type + nullable

→ 知道 YIELD 是 NUMBER，TEST_TIME 是 DATE

✅ Full Information（CHESS 策略）

TABLE: CP_WAFER
COLUMNS:
  LOT_ID     VARCHAR2(20) NOT NULL  -- 批次識別碼
  WAFER_ID   VARCHAR2(5)  NOT NULL  -- 晶圓識別碼
  YIELD      NUMBER(7,4)            -- 良率 (ex: 0.9523, 0.8800)
  VALID_FLAG NUMBER(1,0)            -- 1=有效 0=作廢
FOREIGN KEY: LOT_ID → CP_LOT.LOT_ID
SAMPLE VALUES:
  YIELD: [0.9850, 0.9123, 0.8741]
  VALID_FLAG: [0, 1]

關鍵洞察

CHESS 論文發現光是加上 sample values，精準度提升 8-12%。原因是：

  • YIELD = 0.9850 → LLM 知道這是 0~1 的小數，不是百分比
  • VALID_FLAG: [0, 1] → LLM 知道用 = 1 而不是 = 'Y' 或 = TRUE

你的 YAML 已經做了這件事（VALID_FLAG: "有效旗標（1=有效 0=作廢）"），只是沒有塞真實的 sample values 進去。

Q2. WrenAI 的意圖分類

WrenAI 在每次查詢進來時，先呼叫一個 LLM（不是生成 SQL 的那個），只做一件事：分類。

實際 Prompt 結構

[System]
你是一個查詢意圖分類器。根據資料庫 schema 和使用者問題，
將問題分類為以下四種之一：
- TEXT_TO_SQL: 問題可以用 SQL 查詢回答
- GENERAL: 一般性問題，不需要查 DB（例：什麼是良率？）
- USER_GUIDE: 問系統怎麼用（例：我怎麼查批次資料？）
- MISLEADING_QUERY: 問題模糊或無法查詢（例：哪個最好？）

輸出 JSON：
{ "classification": "TEXT_TO_SQL",
  "rephrased_question": "查詢批次 L001 所有晶圓的良率",
  "reasoning": "問題明確指定批次號和查詢目標，可生成 SQL" }

[User]
Schema: CP_WAFER (LOT_ID, WAFER_ID, YIELD...)
問題: 查一下 L001 的晶圓狀況

實際效果（舉例）

使用者輸入 分類結果 後續動作
查 L001 所有晶圓的良率 TEXT_TO_SQL 進入 SQL pipeline
良率是什麼意思 GENERAL 直接回答，不查 DB
哪個批次最好 MISLEADING 回覆：「請問是指哪個時間範圍？哪個產品？」
我怎麼查 CP 資料 USER_GUIDE 回傳使用說明
刪掉 L001 的資料 MISLEADING 回覆：「本系統僅供查詢，不支援資料修改」

重要：rephrased_question 的作用是把口語化問題標準化：

  • 原始：「查一下上週 CP 的狀況」
  • 改寫：「查詢 2026-04-21 至 2026-04-27 期間所有 CP_LOT 的批次與良率」

這個改寫後的版本才會進入後續的向量搜尋和 SQL 生成。

Q3. 輕量分類 Prompt 怎麼做

不用複雜架構，一個 prompt call 就夠，關鍵是定義好分類規則：

INTENT_CLASSIFIER_PROMPT = """
你是查詢分類器。根據使用者的問題，輸出 JSON 分類結果。

資料庫模組: {available_modules}
(CP=晶圓針測, WAT=電性測試)

分類規則：
- TEXT_TO_SQL: 明確想查數據、批次、良率、比較、趨勢
- AMBIGUOUS:   問題缺少必要資訊（時間/批次/產品）才能查
- KNOWLEDGE:   問概念定義、公式、規則（不需查DB）
- INVALID:     要求修改資料、系統無法處理的請求

輸出格式：
{
  "intent": "TEXT_TO_SQL | AMBIGUOUS | KNOWLEDGE | INVALID",
  "missing_info": ["時間範圍", "批次號"],  // 只在 AMBIGUOUS 時填
  "rephrased": "標準化後的問題",
  "clarify_question": "請問要查哪個時間範圍的資料？"  // 只在 AMBIGUOUS 時填
}

使用者問題: {user_question}
"""

判定邏輯舉例

輸入: "查一下良率"

{
  "intent": "AMBIGUOUS",
  "missing_info": ["時間範圍", "產品或批次"],
  "clarify_question": "請問要查哪個產品、哪段時間的良率？"
}

輸入: "查 L2024-001 這個批次的每片晶圓良率"

{
  "intent": "TEXT_TO_SQL",
  "rephrased": "查詢批次 L2024-001 的 CP_WAFER 各 WAFER_ID 對應 YIELD 值"
}

輸入: "良率怎麼計算的"

{
  "intent": "KNOWLEDGE"
}

→ 直接從 business YAML 的 businessRules 回答，不進 SQL pipeline

Q4. WrenAI Column-level filtering + CoT Reasoning

以真實例子示範完整流程：

使用者輸入：查 L001 批次的晶圓良率分布

Step 1 — Table Retrieval（向量搜尋）

Input: "查 L001 批次的晶圓良率分布"

向量搜尋命中：

Table Score 說明
CP_WAFER 0.91 含 YIELD, WAFER_ID
CP_LOT 0.85 含 LOT_ID
CP_BIN_SUMMARY 0.62
WAT_RESULT 0.31 ← 分數低，不納入

Output: 候選 tables = [CP_WAFER, CP_LOT, CP_BIN_SUMMARY]

Step 2 — Column Filtering + CoT（LLM 輔助）

Input:

  • 問題: "查 L001 批次的晶圓良率分布"
  • 候選 Schema:
    • CP_WAFER: LOT_ID, WAFER_ID, TOTAL_DIE, PASS_DIE, FAIL_DIE, YIELD, TEST_TIME, VALID_FLAG
    • CP_LOT: LOT_ID, PRODUCT_ID, FAB_ID, WAFER_COUNT, PROCESS_NODE, START_TIME, END_TIME, VALID_FLAG, CREATE_TIME, UPDATE_TIME
    • CP_BIN_SUMMARY: LOT_ID, WAFER_ID, BIN_NO, DIE_COUNT

LLM 推理過程（chain_of_thought_reasoning）:

"使用者想查 L001 批次的晶圓良率分布。 需要 CP_WAFER 的 WAFER_ID（識別每片）和 YIELD（良率）。 LOT_ID 是 JOIN 條件，VALID_FLAG 是過濾條件。 CP_LOT 只需要 LOT_ID 做 JOIN，其他欄位不需要。 CP_BIN_SUMMARY 是 Bin 分布，與良率無直接關係，不需要。 因此最終選用: CP_WAFER(LOT_ID, WAFER_ID, YIELD, VALID_FLAG)"

Output:

selected_tables: [CP_WAFER, CP_LOT]
selected_columns:
  CP_WAFER: [LOT_ID, WAFER_ID, YIELD, VALID_FLAG]
  CP_LOT:   [LOT_ID]  ← 只留 JOIN 用的欄位
excluded: CP_BIN_SUMMARY (不相關), CP_WAFER.TOTAL_DIE/PASS_DIE/FAIL_DIE/TEST_TIME (不需要)

Step 3 — 精簡後的 Context 進 SQL 生成

Input（只有過濾後的 schema）:

TABLE CP_WAFER: LOT_ID, WAFER_ID, YIELD, VALID_FLAG
TABLE CP_LOT:   LOT_ID
JOIN: CP_WAFER.LOT_ID = CP_LOT.LOT_ID
RULE: VALID_FLAG = 1
Oracle dialect: FETCH FIRST n ROWS ONLY

Output SQL:

SELECT w.WAFER_ID, w.YIELD
FROM SEMI.CP_WAFER w
JOIN SEMI.CP_LOT l ON w.LOT_ID = l.LOT_ID
WHERE l.LOT_ID = 'L001'
  AND w.VALID_FLAG = 1
ORDER BY w.WAFER_ID
FETCH FIRST 100 ROWS ONLY

Column filtering 的效益：把 15 個欄位壓縮到 4 個，避免 LLM 把不相關欄位（如 CREATE_TIME, FAB_ID）硬塞進 SELECT。

Q6. YAML 字典 vs WrenAI MDL

結論：你不需要 MDL，你的設計已經超越它。

功能 WrenAI MDL 你的 YAML
Table + Column 定義 ✅ ✅
欄位說明（comment） ✅ ✅ 更詳細
JOIN 關係 ✅ ✅ joinPatterns + FK
業務規則 ✅ metrics ✅ businessRules + sqlPattern
查詢範例 ✅ ✅ queryPatterns + SQL
Oracle 方言規則 ⚠️ 透過 sql_functions ✅ _global_rules.yaml 完整
觸發關鍵詞 ❌ ✅ triggerKeywords
軟刪除偵測 ❌ ✅ autoDetected.softDeleteColumn
機器可執行 ✅（Wren Engine 解析） ❌ 需要自己的 loader

你唯一缺的是「loader + injector」——也就是一個把這些 YAML 在 runtime 正確讀出來、塞進 context 的程式邏輯。內容你已經有了，差的是管道。

Q7. question_recommendation 和 data_assistance

data_assistance（問題模糊時的引導）

DATA_ASSISTANCE_PROMPT = """
使用者問了一個模糊問題，無法直接生成 SQL。
請根據可用的資料模組，提供 2-3 個具體可查詢的方向建議。
限制 100 字以內。

可用模組: CP（晶圓針測）、WAT（電性測試）
使用者問題: "{ambiguous_question}"
缺少資訊: {missing_info}

回覆格式：
"你的問題需要更多資訊才能查詢。你可以這樣問：
 • [具體問法 1]
 • [具體問法 2]
 請問你想查哪一種？"
"""

實際例子：

使用者: "幫我看一下最近的狀況"

data_assistance 輸出:

你的問題需要更多資訊才能查詢。你可以這樣問：

  • 「查本週 CP 批次的平均良率」
  • 「查最近 7 天有哪些批次良率低於 90%」
  • 「查 WAT_LOT 本月新進批次清單」

請問你想查哪一種？

question_recommendation（系統主動推薦）

從 YAML 的 queryPatterns + triggerKeywords 自動產生，不需要複雜的 LLM：

def recommend_questions(user_query: str, loaded_modules: list) -> list:
    """
    1. 用 user_query 比對所有模組的 triggerKeywords
    2. 命中的模組 → 取出 queryPatterns
    3. 回傳 3-5 個推薦問題
    """
    recommendations = []
    for module in loaded_modules:
        for pattern in module["queryPatterns"]:
            if any(kw in user_query for kw in pattern["triggers"]):
                recommendations.append({
                    "description": pattern["description"],
                    "id": pattern["id"]
                })
    return recommendations[:5]

效果：

使用者輸入: "CP 良率"

推薦問題（來自 queryPatterns）:

  1. 查詢指定批次的晶圓良率 [QP-CP-001]
  2. 查詢產品別批次清單與晶圓數 [QP-CP-003]
  3. 查詢指定晶圓的 Bin 分佈 [QP-CP-002]

使用者點選 → 帶入完整標準問句 → 直接進 SQL pipeline

好處：不靠 LLM、零成本、零隨機性，使用者點選後問題就已經是標準格式，可以 100% 命中 queryPatterns SQL 範例。
